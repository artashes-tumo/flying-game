# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Flight School – The 4 Forces Game": a 2D teaching game about lift, weight, thrust and drag. The **whole game is one file, `index.html`** (HTML + CSS + one script). There is no build step, no package manager, no tests framework and no external files: fonts are embedded as base64 (the first ~12 lines; skip them when reading), and every picture is drawn in code (canvas paths). It must keep working offline. `README.md` is the player/teacher documentation (features, controls, code map, a click-through test checklist); `READMEv11.md` and the PDFs are older notes.

## Running and checking

- Play: open `index.html` in a browser. `?layout=desktop|cockpit|portrait` forces a layout (cockpit = phone sideways, portrait = phone upright).
- For browser automation, serve the folder over http (e.g. `python3 -m http.server`) rather than `file://`, so `localStorage` behaves.
- Syntax check of the game script (there is no linter):
  ```bash
  awk '/^<script>$/{f=1;next} /^<\/script>$/{f=0} f' index.html > /tmp/game.js && node --check /tmp/game.js
  ```
- Manual tests: the "Test checklist" section of `README.md`.

## Code conventions

Plain ES5 (`var`, `function`, no modules, no arrow functions, no classes) inside one IIFE, compact lines, short comments in the style of the existing ones. No external libraries or CDNs. Keep the hand-drawn notebook look (ink outlines, pastel fills, Patrick Hand font), the three layouts, the dark / high-contrast themes, the colour-blind palette (force colours come from CSS variables via `readColors()` → `FC`), and Reduce motion (`ST.reduceMotion`). Redraws are on demand: call `markDirty()` after changing anything visible while the game is not running.

## Architecture (all inside the IIFE in `index.html`)

**Data tables, edited instead of code.** Most features are driven by plain data:
- `LOCS` (locations, star thresholds) and `RAW` (scenarios) → `makeScn()` → `SCN` / `SBY`. A scenario's `craft` is its suggested plane; `plane:{weight,fuel,fail,…}` in `RAW` is per-scenario physics, not the plane choice. Per-goal star checks live in `OBJ`.
- `LESSON_RAW` (guided lessons, same fields as `RAW` plus `steps`) → `LESSONS`, run by `lessonBegin()` / `lessonTick()`.
- `PLANES` (physics factors, texts, `needs` = suitability limits, paints) and `PAINTS`.
- `ACTIONS` (rebindable keys) and `SCHEMA` (the Settings dialog is generated from it), `ACH` (achievements), `MUSIC`.

**Physics.** `step(dt)` at a fixed 1/60 s. It reads the flying plane's numbers from `PL` (built by `planePhys()` from `PLANES` as factors on the constants `KL`, `KD0`, `KDI`, `TMAX`, `M_H`, `M_V`, `ROLL`, `BRAKE`, `BURN`, `AOA_*`). With the Trainer these are exactly the original constants: the Trainer must keep flying number-for-number the same. Which plane flies is decided by `flightPlaneId()` (lessons → Trainer, daily/endless → suggested plane, otherwise the player's choice if `planeIssue()` allows it). Texts that quote plane numbers use `fmtP()` tokens like `{crit}`, `{rot}`, `{glide}`.

**Drawing.** `draw(t)` picks a renderer through the camera system (`CAMS`, `CAM`, `camResolve()`, `viewKind()`): `drawSideView()` (chase, wide, close-up, runway cam; a world pass through the `CAM` transform), `drawCockpitView()` (pseudo-3D window + instrument panel) or `drawPathView()`, then a shared screen-space pass (labels, glide-path box, force arrows via `drawForceArrows()` which also fills `HIT` for the tooltips, messages). Expensive things are drawn once into sprite canvases (sky, clouds, hill layers, the plane, the cockpit panel) and rebuilt when theme or resolution (`RS`) changes.

**Plane drawings and the pilot anchor.** All plane art is in `LOOKS` (one entry per plane id, next to `PLANE_DEF`, the Trainer's part list):
- Each plane is drawn in a 440 × 140 box, nose to the right, centred on (220,70) = the force-arrow anchor, at scale `sc`. `parts` is a list of `[SVG path, fill, weight]` (fills `body`/`stripe` come from the paint; `glass` is see-through over `seat`; weight `-1` = faint panel/hinge/antenna lines). Also: `far` (far-wing hint), `reg` (registration letters), `elev` (elevator hinge, moves with pitch input), `props`, `jet`, `gear` (the jet's retractable legs, animated by `GEARP` / `gearTarget()`), `lights`, `ck` (cockpit-view frame and engine gauge).
- `contacts` are the wheel/tail bottoms: `wheelDrop()` puts the lowest one exactly on the ground line, so drawing never disagrees with the physics. `arrows` are the arrow start offsets (base px). `sit` = tail-wheel plane (rests on its tail when slow, `sitRot()`).
- **`pilot: {x, y, r}`** is the pilot's head centre and radius in box units, inside the cockpit window in front of the empty seat. The pilot layer (`drawPilotIn()`) is drawn there, between the `seat` part and the `glass` part (the glass is drawn semi-transparent so whatever is behind it shows). To place it on screen, rotate by `planeRot(pitch)` and scale by `sc` around (220,70), as `drawPlane()` does.
- One routine draws every appearance: `drawAirframe()` (static parts) + `drawLive()` (elevator, props, gear, jet heat, lights). `buildPlaneSprite()` caches the in-game sprite per plane/paint/theme/RS; `drawPlane()` is used by the side views, the flight-path view and the touchdown replay; `planePicURL()` / `planeImg()` render the same drawing into cached PNG pictures for the Hangar cards, the briefing card, the result screen and the warm-up.

**The pilot (cosmetic only).** Everything sits right after `planeImg()`: the option tables (`PSKIN`, `PHAIR`, `PHAIRCOL`, `PEYES`, `PBROWS`, `PMOUTH`, `PEXTRA`, `PHEAD`, `PJACKET`, `PBADGE`, `PEXPR`), `PILOT_DEF` and `RANKS`. An option's third element is a lock `req` (`{stars}`, `{ach}` or `{scn:[ids]}`, checked by `reqOpen()`). The saved pilot is `PG.pilot` (null = default); always read it through `pilot()` (cleaned by `normPilot()`, cached until `saveProgress()`), write it with `savePilot()`. `drawPilot(g, P, {expr, body, px, simple})` is the one drawing: head radius 10 units around (0,0), shoulders to y = 24, five expressions; `pilotImg()` / `pilotPicURL()` make cached pictures for HTML. In planes, `drawLive()` calls `drawPilotIn()` when `st.pilot` is set: it clips to the window containing the anchor (`pilotGlass()`, or the biplane's `rim`) and redraws the airframe from that window on with `drawAirframe(g,L,C,from)`. `pilotMood()` gives the in-flight face. The Pilot tab is `hangarPilotHTML()` / `bindHangarPilot()` in `HANGAR_TABS`; the licence card is `showLicence()`; `PG.planes` counts flights per plane. It must never touch physics or stars.

**Explanation levels and the text table.** `ST.level` is `explorer` / `student` / `pilot` (`lvl()`, `lvlE()`, `lvlP()`); it changes only words and detail, never physics, checks or scoring. Player-facing messages live in one table `TX` (next to `fmtP()`): `TX.key = {e: …, s: …, p: …}`, read with `tx(key, vals)`, which picks the level, falls back to the Student text (`s`) when a level is missing, fills `{name}` placeholders from `vals` (format numbers in the caller with `vsStr()` / `altStrFt()` / `spdStrKt()`, which follow the units) and then runs `fmtP()` for plane numbers (`{rot}`, `{crit}`, …). Short phone versions of coach messages are `TX['x.'+key]`. To add a message: add `TX.mykey={s:'…', e:'…', p:'…'}` and call `tx('mykey',{…})`; Explorer texts use no units or numbers (`eSpeed()`, `eHeight()`, `eSink()` turn numbers into words). Users of the table: `computeCoachFull()` / `computeCoach()`, force tips (`tip.*`), meter hints (`m.*`), grade names (`g.*`), check names and briefing lines (`st.*`, `ck.*` via `checkLine()`), results (`resSay`, `say.*`, `well`/`next`, Explorer `ew.*`/`et.*`, Pilot `pilotNumsHTML()` with `pn*`/`pt.*`), the stall pause text (`pauseStall`). Lessons keep their steps in `LESSON_RAW`; `LESSON_LV` adds Explorer step texts (`sayE`, used by `lessonSay()`) and the Pilot "physics" box (`lessonPhysics()`). How to play (`learnBody()`) has per-level versions of Four forces and Landing guide; achievements use `achD()` (`de`/`dp` fields). Level-dependent display: `updateUnitLabels()`, `updatePanel()` (Explorer words, Pilot decimals), `syncSliders()` (Pilot C_L), canvas labels (`cvF()`, `hillTag()`). Units are derived in `applySettings()`: metric only at Pilot with `ST.unitSys==='metric'`. The level is chosen once on the first visit (`levelOffer()` → greeting `levelHello()` → age question `levelAsk()`, which maps an age range to a level and saves only the level; flag `flightSchoolLevelAsked`) and in Quick settings (`QUICK`).

**Input mode (touch or keys).** One place decides it: `INPUT` / `touchUI()` / `setInputMode()` next to `IS_TOUCH`. It starts from `(pointer: coarse)` + `(hover: none)`, switches to keys on the first real (trusted) key press and back to touch after a touch with no key for 20 s, and sets `data-input` on `<html>`. Use `touchUI()` for hint texts (`kThr()` & co., coach touch variants, `tourDefs()`, `resumeTxt()`, the pause and menu hints) and the classes `.keyonly` / `.touchonly` in HTML (CSS hides them; the KEYS panel `#gKeys` hides on touch). Settings rows can take `when:function(){…}` to show only for one input (key re-binding hides on touch). `IS_TOUCH` (the pointer itself) still picks the layout in `calcLayout()`, the pixel ratio and vibration, so layouts never jump when the input changes; `applyLayout()` re-picks the layout on resize and rotation without touching the flight; `?layout=` still overrides.

**Compact pause menu.** `renderPause()` draws the small card (Continue, Restart, mute + volume, gear, house with an inline confirm `#pmConfirm`); the gear opens `#pmqCard` on top (`openPauseQuick()` / `renderPauseQuick()` / `closePauseQuick()`: Quick settings, More settings, Level select). Esc closes the gear card first (`handleEsc()`); the hook for a desktop "Quit game" (`window.flightSchoolHost.quit`) sits in the house confirm.

**Compact Hangar.** Both tabs are a preview on top (`.hgtop`) plus horizontal rows built by `hrowHTML()` and wired by `bindHrows()` (wheel → sideways, ← → between items, ‹ › buttons on mouse devices). Plane tab: `hangarPlaneHTML()` / `bindHangarPlane()` with `hgView` (the plane shown; clicking a plane you may fly also selects it). Pilot tab: `hangarPilotHTML()` with the group tabs `PGROUPS` / `pilotGroup` (Face is one row of labelled sub-groups). Short screens (`max-height:460px`) get tighter CSS so the Hangar fits without vertical scrolling.

**Panel animations.** One helper next to `openModal()`: `fxOpen(el)` / `fxClose(el, hide, done)` (and `fxSwap(el)` for a tab cross-fade). The element's `data-fx` picks the motion in CSS (`rise` briefing/results/licence, `slide` Hangar/achievements, `right` Settings, `pop` pause menu, `side` the pause gear card, `fade` the screens layer, `note` notifications); `.fx-in` is the open state, `.fx-out` blocks clicks while closing. Panels whose logic uses the `show` class (`#modal`, `#settings`) carry `data-fx-hide="class"`, so `show` changes at once (logic stays correct) while the motion finishes; others use the `hidden` attribute after the close. Opening during a close cancels the pending hide. Use `openOverlay(html, fx)` / `openModal(html, keep, fx)` for a new dialog. Reduce motion: a very short fade, no transforms. Screen-to-screen moves keep the `.scrin.anim` slide (forward / back).

**Notifications.** `notify({kind, label, icon, title, line, ach})` queues a card (`NOTE_Q`, `noteNext()`, `noteHide()`) in `#note`; one at a time, about 4 s, hover pauses, click opens `showAch(id)` with that achievement highlighted, × closes. `grant()` calls `noteAch()` for every new achievement; `showEnd()` takes `unlockSnap()` before and calls `noteUnlocks()` after (new location, rank-up, paint, pilot item). Sound: `sfxUnlock()` (effects volume and mute). Announced with `srSay()`. In a flight it is smaller and placed below the phone HUD; it never takes focus or pauses.

**Condition tags.** `TAGS` (icon, word, meaning) and `scnTags(s)` (only the plane tag when the scenario's plane is not the Trainer); `tagHTML(t, focusable)` and `iconKeyHTML()` (a `<details>` popover; Esc closes it first). Colours are CSS custom properties per tag (`.tag-wind{--tb:…}`) with dark-theme versions and one black/white style for high contrast; a tag always shows an icon and a word. Used on the scenario cards (`scnCardHTML()`) and the briefing (`showBriefing()`, sections plus `briefConds()` for the condition rows at the player's level).

**Screen structure.** The page opens on the main menu (`showScreen('main')` at the end of the script). Menu screens live in one full-page layer `#screens` (z 45) and are listed in `SCREENS` (`main`, `levels`, `loc` with a location id, `learn`): `showScreen(id, arg, {back, same, stack, overFlight, focus})`, `screenBack()` (Back button and Esc pop `SCR_STACK`), `closeScreens()` (called by `startFlight()`). Opened during a flight with `overFlight` the flight waits paused and the last Back returns to it. Their code sits just above "map screen + briefing card": `mainHTML()` (with the 🏆 Achievements button) + `drawMenuBg()`, `levelsHTML()` (`locCardHTML()`, `sceneSVG()`, `modesHTML()`: Daily and Endless), `locHTML()` (`scnCardHTML()`, `scnIcons()`), `learnHTML()` / `learnBody()` (`LEARN_TABS`; the warm-up is `matchHTML()` / `bindMatch()`). `showMap()` is now only a redirect to the level select. Dialogs (briefing, Hangar, licence, achievements) open on top in `#modal`; `closeIntro()` returns to the screen underneath (`redrawScreen()`). `MENU` (`flightSchoolMenu`) keeps the last scenario, location and How-to-play tab. The pause menu `#pauseMenu` (z 48) shows whenever a flight is paused: `updatePauseUI()` → `openPause()` / `renderPause()`; it embeds Quick settings. Quick settings are one list `QUICK` rendered by `quickHTML(prefix)` (Settings → Quick and the pause menu) with one handler `settingInput()`; `syncQuick()` keeps copies in step. `window.flightSchoolHost.quit` is the hook for a desktop "Quit game" button.

**Menu scene and menu plane.** The background of the menus is drawn by the block "the menu scene" (just after `bindMain()`): `MS` is the scene state and `msBuild(loc)` caches per location, theme and time of day a still base (sky, sun/moon/stars, ground or sea, runway) plus the three scrolling layers from `drawLayerShapes()` (clouds from `drawCloudShape()` in `msClouds()`). `clockTod()` picks day/dusk/night from the player's clock; `menuLocs()` limits the cross-fading rotation to unlocked locations; `msLife()` / `msLifeStep()` draw the windsock, runway lights, boats, birds, a balloon or glider and a distant Hangar plane. `MPL` is the steerable menu plane (`mpStep()` simple forgiving motion, no physics; `mpDraw()` uses `drawAirframe()` / `drawLive()` with the pilot, plus small force arrows `msArrow()`; `mpSound()` a soft engine hum). Input: pointer handlers on `#scr` (empty sky only), and `mpKey()` called from the main keydown handler (arrows steer only when no button is focused; otherwise they move between the main menu buttons). `menuBgStart()` / `menuBgStop()` / `drawMenuBg()` run the loop only while the main menu is visible and the tab is shown; other screens get one still frame; Reduce motion makes it a still picture with no steering.

**UI screens.** Modal screens share `openModal()` / `openOverlay()` / `closeIntro()` (briefing `showBriefing()`, Hangar `showHangar()` with tabs from `HANGAR_TABS`, results `renderEnd()`, intro, achievements). Phone layouts are handled by `applyLayout()`, `openSheet()`, `openMenu()`. Keyboard handling is one `keydown` listener: Esc first closes open panels and dialogs, then goes back one menu screen (`handleEsc()`); only in a flight does it run its action (`escKey()`, which also does the two-press Esc in fullscreen).

**Saved state (`localStorage`).** `flightSchoolSettings3` (settings + key bindings; `keyVer` and `migrateKeys()` move old defaults), `flightSchoolProgress3` (stars `PR`, achievements/daily/endless/lessons, the pilot `PG.pilot` and flights per plane `PG.planes` in `PG`), `flightSchoolHangar` (plane and paints), plus small flags (`flightSchoolSeen`, `flightSchoolTour`, `flightSchoolScenario`, `flightSchoolPilotOffer`, `flightSchoolMenu`, `flightSchoolLevelAsked`, …). Old saves must keep loading: when adding fields, default them.
